Bash (Bourne Again SHell) is the default shell on most Linux distributions. It is both an interactive command interpreter and a scripting language for automating tasks. Its great strength is gluing together small programs; its great weakness is that subtle quoting and word-splitting rules cause bugs that only surface on the one filename with a space in it. Most of this page is about writing Bash that *doesn't* break on those edge cases.

## Script Structure

```bash
#!/usr/bin/env bash
# Shebang tells the OS to run this with bash

set -euo pipefail   # recommended: exit on error, unbound vars, pipe failures

echo "Hello, world!"
```

```bash
# Make a script executable and run it
chmod +x myscript.sh
./myscript.sh
```

<Aside type="tip" title="Why `/usr/bin/env bash` and not `/bin/bash`?">
`#!/usr/bin/env bash` looks up bash on the user's `PATH` rather than hard-coding a location. This matters on systems where bash lives somewhere non-standard (macOS with Homebrew, some BSDs, Nix). Hard-coding `/bin/bash` is fine for system scripts on a known distro but less portable.
</Aside>

## Variables

```bash
name="Alice"            # no spaces around =
echo $name              # print variable
echo "${name}s"         # brace syntax — use when concatenating

readonly PI=3.14        # constant
unset name              # delete variable

# Command substitution
today=$(date +%Y-%m-%d)
files=$(ls /etc/*.conf | wc -l)
echo "Today: $today, config files: $files"
```

<Aside type="caution" title="The single most common Bash bug">
**Always quote your variable expansions**: `"$var"`, not `$var`. Unquoted, Bash splits the value on whitespace and expands glob characters (`*`, `?`). A file named `my report.txt` becomes *two* arguments `my` and `report.txt`; a variable containing `*` expands to every file in the directory. The rule of thumb: if you're not certain you want splitting and globbing, quote it.

```bash
file="my report.txt"
rm $file        # WRONG: tries to remove 'my' and 'report.txt'
rm "$file"      # CORRECT: removes 'my report.txt'
```
</Aside>

### Special Variables

| Variable | Meaning |
|---|---|
| `$0` | Script name |
| `$1`, `$2`... | Positional arguments |
| `$#` | Number of arguments |
| `$@` | All arguments (as separate words) |
| `$*` | All arguments (as one string) |
| `$?` | Exit code of last command (0 = success) |
| `$$` | PID of current shell |
| `$!` | PID of last background process |

<Aside type="note" title='"$@" vs "$*"'>
Quoted `"$@"` expands to each argument as a *separate* word — this is almost always what you want when forwarding arguments to another command. Quoted `"$*"` joins everything into a *single* word. Use `"$@"` by default.
</Aside>

## Parameter Expansion

Bash can manipulate variables without calling external tools like `sed` or `cut` — faster and dependency-free.

```bash
file="/var/log/syslog.1.gz"

echo "${file##*/}"      # syslog.1.gz   — strip longest leading */ (basename)
echo "${file%/*}"       # /var/log      — strip trailing /* (dirname)
echo "${file%.gz}"      # .../syslog.1  — remove .gz suffix
echo "${file#*.}"       # 1.gz          — remove up to first .

name="Alice"
echo "${name:-Guest}"   # Alice; if unset/empty → "Guest" (default value)
echo "${name:=Guest}"   # like above but also assigns it
echo "${#name}"         # 5 — string length
echo "${name^^}"        # ALICE — uppercase
echo "${name,,}"        # alice — lowercase
echo "${name/A/4}"      # 4lice — replace first match
```

| Pattern | Effect |
|---|---|
| `${var:-default}` | Use `default` if `var` unset/empty |
| `${var:=default}` | …and assign it back |
| `${var:?msg}` | Error and exit if `var` unset |
| `${var#pattern}` / `${var##pattern}` | Strip shortest / longest prefix |
| `${var%pattern}` / `${var%%pattern}` | Strip shortest / longest suffix |
| `${var/old/new}` / `${var//old/new}` | Replace first / all |

## Conditionals

```bash
# if / elif / else
if [ "$1" = "hello" ]; then
    echo "Hello to you too"
elif [ "$1" = "bye" ]; then
    echo "Goodbye"
else
    echo "Unknown: $1"
fi

# Numeric comparison
if [ "$count" -gt 10 ]; then
    echo "More than 10"
fi

# File tests
if [ -f "/etc/hosts" ]; then echo "file exists"; fi
if [ -d "/tmp" ];       then echo "is a directory"; fi
if [ -z "$var" ];       then echo "variable is empty"; fi
if [ -n "$var" ];       then echo "variable is not empty"; fi
```

### Comparison operators

Numeric and string comparisons use *different* operators — a frequent source of confusion.

| Numeric | String | Meaning |
|---|---|---|
| `-eq` | `=` / `==` | Equal |
| `-ne` | `!=` | Not equal |
| `-gt` | `>` * | Greater than |
| `-lt` | `<` * | Less than |
| `-ge` / `-le` | — | Greater/less or equal |

\* Inside `[[ ]]`, `<` and `>` compare strings lexically. Using `>` in `[ ]` is interpreted as redirection — another reason to prefer `[[ ]]`.

### [[ ]] vs [ ]

Prefer `[[ ]]` in modern bash — it supports regex, `&&`/`||` inside the test, and doesn't word-split variables.

```bash
if [[ "$name" == A* ]]; then echo "starts with A"; fi
if [[ "$str" =~ ^[0-9]+$ ]]; then echo "all digits"; fi
if [[ -f "$file" && -r "$file" ]]; then echo "readable file"; fi
```

For arithmetic, `(( ))` is cleaner still:

```bash
if (( count > 10 )); then echo "big"; fi   # no $ needed, real math operators
(( total = price * qty ))
```

### case statements

For matching one value against many patterns, `case` is more readable than a long `if/elif` chain:

```bash
case "$1" in
    start)        echo "Starting...";;
    stop|halt)    echo "Stopping...";;       # multiple patterns with |
    *.txt)        echo "A text file";;        # glob patterns work
    *)            echo "Unknown: $1";;        # default
esac
```

## Loops

```bash
# for loop over a list
for fruit in apple banana cherry; do
    echo "Fruit: $fruit"
done

# for loop over files
for file in /etc/*.conf; do
    echo "Processing $file"
done

# C-style for loop
for (( i=1; i<=5; i++ )); do
    echo "$i"
done

# while loop
count=0
while [ "$count" -lt 5 ]; do
    echo "$count"
    (( count++ ))
done

# Read lines from a file
while IFS= read -r line; do
    echo "Line: $line"
done < /etc/hosts
```

<Aside type="caution" title="Never `for line in $(cat file)`">
A tempting but broken idiom is `for line in $(cat file)`. It splits on *every whitespace character*, not just newlines, so a line with spaces becomes multiple iterations, and globs in the file get expanded. The correct way to read a file line by line is the `while IFS= read -r line` pattern shown above:
- `IFS=` prevents trimming of leading/trailing whitespace,
- `-r` stops backslashes being interpreted as escapes.
</Aside>

## Functions

```bash
greet() {
    local name="$1"           # local variable — not visible outside function
    echo "Hello, $name!"
    return 0                  # return code (not a value)
}

greet "Alice"
greet "Bob"

# Capture function output
result=$(greet "Charlie")
```

<Aside type="note" title="Functions return codes, not values">
A Bash function's `return` only sets an exit status (0–255), like any command — it is **not** a return value. To pass data back, the function writes to stdout and the caller captures it with `$(...)`, as in `result=$(greet "Charlie")`. Always declare function-internal variables with `local`, or they leak into the global scope and cause spooky action at a distance.
</Aside>

## Input / Output & Pipelines

```bash
# Redirect stdout to file
echo "log entry" >> /var/log/myapp.log   # append
echo "fresh start" > /tmp/out.txt        # overwrite

# Redirect stderr
command 2> error.log
command > out.log 2>&1         # both stdout and stderr to same file

# Pipelines
cat /etc/passwd | grep "alice" | cut -d: -f1,3
ps aux | sort -rk3 | head -5   # top 5 by CPU

# Here string
grep "pattern" <<< "search in this string"

# Here document — feed a multi-line block as stdin
cat <<EOF > /etc/myapp.conf
host = localhost
port = 8080
EOF
```

<Aside type="tip" title="Useful text tools to pipe into">
The classic Unix filters that make pipelines powerful: `grep` (filter lines), `cut` (extract columns), `sort`, `uniq -c` (count duplicates), `tr` (translate/delete chars), `sed` (stream edit), `awk` (field-aware processing), `head`/`tail`, `wc` (count). Composing these often replaces what would be a whole script in another language.
</Aside>

## Arrays

```bash
fruits=("apple" "banana" "cherry")
echo "${fruits[0]}"          # first element
echo "${fruits[@]}"          # all elements
echo "${#fruits[@]}"         # count

# Append
fruits+=("date")

# Iterate (always quote "${arr[@]}")
for f in "${fruits[@]}"; do
    echo "$f"
done
```

Bash 4+ also has **associative arrays** (key→value maps):

```bash
declare -A capital
capital[Switzerland]="Bern"
capital[France]="Paris"
echo "${capital[Switzerland]}"        # Bern
for country in "${!capital[@]}"; do   # ! gives the keys
    echo "$country -> ${capital[$country]}"
done
```

## Error Handling

```bash
set -e          # exit immediately on error
set -u          # treat unset variables as errors
set -o pipefail # pipeline fails if any command fails

# Trap — run a function on exit/error
cleanup() {
    rm -f /tmp/myapp.lock
    echo "Cleaned up"
}
trap cleanup EXIT

# Check exit codes manually
if ! cp source.txt dest.txt; then
    echo "Copy failed" >&2
    exit 1
fi
```

<Aside type="caution" title="`set -e` is not a magic safety net">
`set -euo pipefail` catches many mistakes, but `set -e` has surprising blind spots: it does *not* trigger inside conditionals, in the left side of `&&`/`||`, or in command substitutions in some contexts. It's a useful default, not a substitute for checking the exit codes of commands that genuinely matter. For anything important, test `$?` or use `if ! command; then ...` explicitly.
</Aside>

## Debugging

```bash
bash -x script.sh       # print every command as it runs (trace mode)
set -x                  # turn on tracing partway through a script
set +x                  # turn it off again
```

<Aside type="tip" title="Run your scripts through ShellCheck">
[ShellCheck](https://www.shellcheck.net) is a static analyser that catches the overwhelming majority of common Bash bugs — unquoted variables, useless `cat`, wrong test operators — before you ever run the script. Many editors integrate it. It's the single highest-value tool for writing correct Bash.
</Aside>

## Practical Script Template

```bash
#!/usr/bin/env bash
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
LOG_FILE="/var/log/myscript.log"

log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "$LOG_FILE"; }
die() { log "ERROR: $*" >&2; exit 1; }

[[ "$#" -lt 1 ]] && die "Usage: $0 <target-dir>"

TARGET="$1"
[[ -d "$TARGET" ]] || die "Directory not found: $TARGET"

log "Starting backup of $TARGET"
tar czf "/backup/$(date +%Y%m%d)-backup.tar.gz" "$TARGET"
log "Done"
```
